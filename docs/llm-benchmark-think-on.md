## 一、这份报告回答什么

用户要求：「单独开启 think 模式，重新跑一轮，保存为新的报告。」
结论先行：**在这台机器上，开思考普遍是负收益**——三个支持思考的模型里，一个持平、两个明显掉分，而单轮耗时涨了 2–4 倍。

## 二、谁参加了这轮

`ollama /api/show` 确认只有三个模型支持 thinking（`thinking.default = true`）：

| 模型 | 支持思考 | think-on 表现 |
| --- | --- | --- |
| gemma4:e4b | ✅ | 正常完成 33 轮 |
| qwen3.5:9b | ✅ | 正常完成，4 轮空回复 |
| gemma4:12b | ✅ | 正常完成，1 场景全部超时 |
| qwen2.5-coder:7b / 14b、deepseek-coder-v2:16b | ❌ | **HTTP 400: "does not support thinking"**，33 轮全部报错 |

后三个模型报告里的 0% 是接口直接拒绝，**不是能力得分**；它们的真实水平见 think-off 报告。这轮对它们本来也没有意义——没有思考能力，「开思考」无从谈起。

## 四、think-on 掉分的两个机制（都查了原始 transcript）

**机制一：思考吃满 token 预算，正文为空。** 引擎给每轮 `max_tokens=3072`，思考 token 和正文共用这个额度。qwen3.5:9b 在 file-organize 第 2、3 轮把 3072 个 token 全花在思考上，`message.content` 返回空串，两轮检查点全挂——这就是它 file-organize 从 100% 崩到 35% 的直接原因。knowledge 第 2 轮同样如此。和 gsm8k 首轮 0 分是同一个问题（那份报告 4.2 节）。

**机制二：单轮 300 秒超时。** gemma4:12b 生成速度只有 4.1 tok/s，一轮长思考（>1200 token）就要 5 分钟以上，code-dev 的 5 轮全部超时记 0 分。这是「慢机器 + 长思考」的物理冲突，换独显机器大概率能救回这个场景。

## 五、结论

1. **日常使用不要开思考。** 质量不升反降（9b/12b 各掉 12+ 分），单轮耗时 2–4 倍（最坏 146 s/轮），在 3072 token 预算下还会出现「想完就没了」的空回复。
2. **思考真正有用的地方是抗注入。** 三个模型的长程指令全部到 100%，think-off 时 9b 只有 77.3%。如果你在意「用户输入里藏了诱导指令」这类攻击，思考值得开。
3. **gemma4:e4b 是唯一开思考不亏的模型**：+0.6 分、0 空回复、40.7 s/轮尚可接受。它的思考长度控制得最好（token 只多 21%，而 9b 翻倍）。
4. **gemma4:12b 在这台机器上不适合开思考**：4.1 tok/s 的基础速度撑不起长思考，超时率太高。

## 六、复现

```bash
# 代理非必需——chatbench 走原生 /api/chat, think 参数合法
python duck_rush/ai/duck-llm-chatbench.py run \
  --models gemma4:e4b qwen3.5:9b gemma4:12b \
  --think on --tag think-on --force --verbose
```

数据落盘于 `~/.duck-rush/data/duck-llm-chatbench-think-on/`，与 think-off 批次（默认目录）并存互不覆盖；逐轮 transcript 里带 `thinking` 字段与 `error` 字段，可复查每一轮的思考原文与失败原因。

## 七、局限

1. 非思考模型无法参与（400 拒绝），本轮只有 3 个模型。
2. `max_tokens=3072` 的预算是引擎固定的，「思考吃满预算」是真实线上行为，但换个预算结论可能变化。
3. 单轮 300 s 超时对 4.1 tok/s 的 gemma4:12b 偏紧；它的 code-dev 0% 主要是超时，不是模型不会做。
4. 33 轮 × 3 模型的采样波动与 think-off 报告同量级（±5pp）。
